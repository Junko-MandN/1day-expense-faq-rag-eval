# 社内FAQ AIの回答品質を比較する — API × RAG × Evals

*Comparing three ways to ground answers in an expense-policy FAQ with the OpenAI API (Python prototype)*

## Summary (English)

A small Python prototype that answers questions from a **fictional** expense policy using the OpenAI API. I compared three ways of giving the model its context on **10 hand-scored test questions**:

- **A:** model only (no policy)
- **B:** the full policy in the prompt
- **C:** simple keyword-retrieval RAG (relevant policy lines only, picked with a small hand-made keyword list; not semantic search)

| | A: model only | B: full policy | C: keyword RAG |
|---|---:|---:|---:|
| Correct vs. expected answer | 4/10 | 10/10 | 8/10 |
| Grounded in the policy | 1/10 | 9/10 | 10/10 |
| Total tokens | 2,890 | 9,352 | 4,432 |

**What I learned**

1. **Right/wrong scoring is not enough.** On Q5 the full-text method answered "yes" and cited the accommodation chapter, which does not actually say so. The retrieval method never received the line about prior approval (a keyword mismatch) and reported that approval was not mentioned in the policy. The policy itself also never states whether approved excess is reimbursable. Scored on accuracy alone, the confident answer wins and the cautious one loses, so I scored grounding and abstention separately.
2. **Check what the model was actually given before blaming the model.** Q5 was a retrieval miss plus an ambiguous policy. Q6 was the opposite: retrieval was complete, but the answer left out an important caution.
3. **Conditions get lost.** On Q10 the full-text method turned "payment *may* be held" into "payment *will* be held", which my three metrics did not capture.

**Limits:** 10 questions, fictional data, one person scoring by hand, keyword (not semantic) retrieval with a hand-made keyword list tuned to this question set, a single run per question, and no re-run after fixes. The improvement ideas in this README are untested.

**How it was built:** I started with no design in mind and worked with ChatGPT, which drafted the initial design and code. I reviewed and approved each proposal, ran the experiments, scored the results by hand and investigated the mismatches myself. `gpt-4.1-mini` was used as a low-cost model.

Raw answers used for scoring: [results.csv](results.csv)

Details: [docs/results.md](docs/results.md) · [docs/analysis.md](docs/analysis.md) · [docs/architecture.md](docs/architecture.md)

## 1. プロジェクト概要

PythonとOpenAI APIを使い、社内の経費精算規程に関するFAQ回答プロトタイプを作成しました。

同じ質問に対して、情報の与え方が異なる3つの方式を比較し、回答の正確性、根拠との整合性、適切な回答保留の観点から回答品質を評価します。

**目的は、AIに回答させることだけではなく、回答品質に影響する要因を理解し、改善につなげることです。**

本プロジェクトで使用する経費規程と質問データは、検証用に作成した架空のデータです。個人の学習として、個人のアカウントと環境で作成しており、勤務先の情報は使用していません。

テーマも構成も、アイデアがない状態から始めました。ChatGPTに初期案とコードの下書きを作ってもらい、相談しながら進めています。出てきた案は自分で読んで採用を判断し、実行、結果の確認、手動での採点、不一致の原因の確認は自分で行いました。

## 2. 検証した3つの方式

| 方式 | 概要 | 検証したいこと |
|---|---|---|
| A：モデル単体 | 規程を渡さず、一般知識で断定しないよう指示して質問を渡す | 規程がない場合、どのような回答になるか |
| B：規程全文 | 経費規程全体を質問と一緒に渡す | 規程を与えることで回答品質が改善するか |
| C：簡易RAG | キーワードで関連する規程行を検索し、質問と一緒に渡す | 必要な情報を絞りながら、回答品質を維持できるか |

3方式に同じ質問セットを与え、回答とトークン使用量を比較しました。

## 3. 技術構成

- Python
- OpenAI API
- モデル：`gpt-4.1-mini`（検証用に比較的安価なモデルを選択）
- JSONによる質問・期待する回答の管理
- テキストファイルによる経費規程の管理
- Pythonによるキーワード検索（固定の検索語リストから質問に含まれる語を拾い、一部の語に同義語を追加）
- トークン使用量の記録

### 処理の流れ

**A：モデル単体**

質問 → OpenAI API → 回答

**B：規程全文**

質問＋経費規程全文 → OpenAI API → 回答

**C：簡易RAG**

質問 → Pythonで規程を検索 → 関連する規程行を抽出 → 質問と検索結果をOpenAI APIに送信 → 回答

C方式では、規程ファイルの検索処理をPython側で行い、抽出した情報をモデルに渡して回答を生成します。この構成により、情報の検索と自然言語による回答生成を、別々の処理として設計できることを確認しました。構成図は [docs/architecture.md](docs/architecture.md) にあります。

## 4. 評価方法

同じ10問の質問セットに対する各方式の回答を `results.csv` に保存し、質問ごとに3方式の回答を並べて表示するスクリプト（`show_q1by1.py`）で見比べながら、1人で目視で採点しました（結果は `evaluation.csv`）。

- **正確性（accuracy）：** 期待回答と一致しているか（1または0）
- **根拠との整合性（grounding）：** 規程に書かれていない内容を、根拠があるかのように断定していないか（1または0）
- **適切な回答保留（abstention）：** 規程から判断できない質問で、推測で回答せず、確認を促せたか。対象は該当する質問だけで、方式ごとに件数が異なる。
- **トークン使用量：** 方式ごとの合計と1問あたりの平均（`token_comparison.csv`）
- **失敗理由・備考：** 不一致や根拠不足があった場合の理由を記録

期待回答自体が規程から読み取れる結論にとどまる質問（Q5）があるため、期待回答の妥当性も別途考慮する必要があります。原因調査の後も、点数は変更していません（修正したのは、失敗理由と備考の説明のみです）。

## 5. 結果と主な発見

各質問の詳細は [docs/results.md](docs/results.md)、Q5・Q6の原因調査は [docs/analysis.md](docs/analysis.md)、構成図は [docs/architecture.md](docs/architecture.md) を参照。

### 5.1 結果の一覧

同じ10問を3方式に与え、手動で採点した。

| 方式 | 期待回答との一致 | 根拠との整合性 | 適切な回答保留 | 合計トークン数 | 1問あたり平均 |
|---|---|---|---|---|---|
| A：モデル単体 | 4/10（40%） | 1/10（10%） | 7/8 | 2,890 | 289.0 |
| B：規程全文 | 10/10（100%） | 9/10（90%） | 1/2 | 9,352 | 935.2 |
| C：簡易RAG（キーワード検索） | 8/10（80%） | 10/10（100%） | 2/2 | 4,432 | 443.2 |

- 10問の小規模な検証であり、1問の違いが10ポイントに相当する。方式の優劣を一般化するものではない。
- 規程は短い架空のデータである。規程が大きくなるほど、全文を渡す方式のトークン数は増えると考えられるが、今回は検証していない。
- 「適切な回答保留」は、評価対象の質問数が方式ごとに異なる（A：8問、B：2問、C：2問）ため、他の指標と同じようには比較できない。
- 「簡易RAG」は意味検索ではなく、キーワードで規程の行を検索する方式である。

### 5.2 A：モデル単体は、規程を根拠にできない

規程を渡さない場合、モデルは会社固有のルールを知らないため、一般論で回答するか、社内規程の確認を促す回答になった。Aには「一般知識で断定せず、会社固有のルールが分からない場合はその旨を伝える」という指示を付けており、この指示が、回答保留（7/8）を増やした可能性がある。指示を付けない素のモデルでは測っていない。期待回答と一致した4問も、規程を根拠にしたものではない（根拠との整合性は1/10）。

### 5.3 B：規程全文は一致率が高いが、トークン数が多い

規程全文を渡すと、条件や例外を明示した回答が得られ、10問すべてが期待回答と一致した。一方、毎回全文を送るため、合計トークン数はCの約2.1倍（9,352と4,432）だった。

### 5.4 C：トークン数は半分程度。ただし、検索の精度が課題

Cは合計トークン数をBの約半分に抑え、根拠との整合性は10/10だった。一方、期待回答との一致は8/10で、一致しなかった2問（Q5、Q6）を調べた（5.5、5.6）。

検索全般では、質問に関係の薄い行も混ざった。Q5では、検索された11行のうち、宿泊費の上限と承認に直接関わる行は3行程度（目視による概算）だった。「精算」というキーワードが多くの行に一致するためである。Q6では、検索された5行がすべて領収書・証憑に関する行だった。

### 5.5 Q5：検索の漏れと、規程の曖昧さが重なったケース

質問：「1泊15,000円のホテルは、事前に所属部門長の承認を得れば精算できますか？」

検索キーワードは「宿泊費」「精算」「ホテル」だった。規程には、次の行がある。

- 国内出張の宿泊費は、1泊あたり12,000円を上限とする。
- 上限を超える宿泊が必要な場合は、予約前に所属部門長の承認を得る。
- 承認を得ずに上限を超えた場合、原則として超過分は精算できない。

このうち、2行目の「承認を得る」の行は、キーワード（「宿泊費」ではなく「宿泊」と書かれている）と一致せず、Cには渡されなかった。さらに、規程全体を読んでも、承認を得た場合に超過分を精算できるという明記や、承認の基準は書かれていない。あえて曖昧さを残した検証ケースである。

| 要因 | 内容 |
|---|---|
| ① 検索漏れ | 承認の行が、キーワードの不一致でCに渡されなかった |
| ② 規程の曖昧さ | 規程全体にも、承認後の精算可否や承認の基準は明記されていない |

各方式の回答は、次のとおりだった。

- **B（規程全文）：**「はい、1泊15,000円のホテルは、事前に所属部門長の承認を得れば精算できます。（第4章 宿泊費の規定による）」と言い切り、根拠として第4章を示した。しかし、第4章に承認後の精算可否は明記されていない。規程にない結論を、規程を根拠にして断定した。期待回答とは一致したが、根拠との整合性は満点にならなかった。
- **C（簡易RAG）：** 渡された行をもとに、上限が12,000円であること、承認なしの超過は原則精算できないことを示し、「事前に所属部門長の承認を得れば」については規程に明記されていないと回答した。渡された情報の範囲では妥当だが、「渡された行にない」ことを「規程にない」と表現している。実際の規程には承認の行があり、Cはそれを見ていない。期待回答とは不一致と採点した。

この結果から、次のことが分かる。

- 正解か不正解かの採点では、「規程にない結論の断定」と「渡された情報の範囲での保留」の差を表せない。
- 検索の漏れは、モデルが保留した、または誤ったように見える回答として現れる。原因を調べるには、実際に渡された規程行を確認する必要がある。

なお、`evaluation.csv` のC・Q5の備考は、当初「規程の曖昧さを正しく指摘」としていたが、検索ログの確認後に「検索漏れを含む」と修正した。点数は変更していない。

### 5.6 Q6：検索で必要な情報は取れていたが、回答で注意点が省略されたケース

質問：「新幹線の領収書を紛失したら、どうすればいいですか？」

検索結果には、「領収書を紛失した場合は、経理担当者に相談する」と、「領収書を紛失したことだけを理由に、精算が自動的に承認されることはない」の両方が含まれていた。しかし、Cの回答は相談先を示したのみで、自動的に承認されないという注意点を含まなかった。

必要な情報は検索で取得できていたため、検索ではなく回答生成の段階で、重要な注意点が省略された可能性がある。ただし、今回は再現実験を行っておらず、原因は確定していない。

### 5.7 Q10：条件付きの表現が、断定形に変わったケース

質問：「領収書などの証憑に不備があったら、支払いはどうなりますか？」

規程には、「確認・修正が完了するまで支払いが保留されることがある」と書かれている。Bは「支払いが保留されます」と断定形に言い換え、Cは「保留される可能性がある」と条件を保持した。結論は大きく外れていないが、規程の確実性の程度が変わっている。

この違いは、3つの評価指標では十分に捉えられない。評価表では、結論が合っているため、Bの根拠との整合性を1とし、備考にのみ記録した。「規程の条件や確実性の程度を保持したか」を、別の評価観点として追加する必要がある。

## 6. 学び：評価と原因の切り分け

### 6.1 正解率だけでは、回答の質を評価しきれない

Q5では、Bが規程にない結論を断定して期待回答と一致し、Cが渡された範囲で保留して不一致になった。正解率だけで見ると、Bが優れて見える。

望ましい回答は、「承認があれば精算できると読めるが、規程に明記はないため、経理に確認する」のように、読み取った内容と不確かさを分けて示す形だと考える。この差を評価するには、採点を「正解か不正解か」の二択ではなく、次のように分ける必要がある。

- 規程に明記された内容に基づいて回答した
- 推論であることを示して回答した
- 規程にない結論を断定した
- 判断を避け、確認を促した
- 規程の条件や確実性の程度（「〜ことがある」など）を保持して回答した

### 6.2 原因は、実際に渡した情報を見るまで分からない

Q5は、結果だけを見ると「AIが保留した」「規程が曖昧だった」と説明できるように見えた。しかし、Cに実際に渡した規程行を確認すると、検索漏れが含まれていた。

回答の問題を、モデルの能力や元データの曖昧さの問題と決めつける前に、次の3つを分けて確認する。

1. 検索で、必要な情報が取得できたか
2. 元データだけで、質問に答えられるか
3. 取得した情報を、回答に反映できたか

### 6.3 人・通常のプログラム・生成AIの役割を分ける

- **人：** 規程や期待する回答を定義する。曖昧なルールを確認する。評価結果をもとに改善方針を判断する。
- **通常のプログラム（Python）：** ファイルを読み込む。キーワードで検索する。質問を順番に処理する。トークン使用量を記録する。
- **生成AI：** 与えられた質問と関連情報をもとに、自然言語で回答を生成する。

明確なルールに従う処理は通常のプログラムに任せ、文章の理解や生成に生成AIを使う。規程自体が曖昧な場合は、システムやAIだけで正しい判断を確定できず、人による確認が必要になる。

### 6.4 全文を渡す方式と検索する方式は、一概に優劣をつけられない

今回の10問では、全文方式は一致率が高く、簡易RAGはトークン数が少なく、根拠との整合性が高かった。ただし、規程が短いこと、質問数が少ないこと、検索がキーワードに限られることから、結果を一般化することはできない。規程の規模、更新頻度、求める精度、コストに応じて選ぶ必要がある。

## 7. 考察：AI活用の進め方

要点は次のとおり。

- **チャットとAPIの違いは、利用場面で説明する。** 単発の質問であれば、チャット型のサービスで十分な場合がある。既存業務への組み込み、定型処理の自動化、出力形式の統一などが必要なときに、APIの価値が出る。
- **作れることと、作る価値があることを分ける。** 既存のツールで目的が達成できるなら、それを使うほうが、開発・保守の負担を抑えられる。
- **役割を組織として定義する。** 利用者が自分で解決する範囲、専門家に相談する基準、エンジニアが提供する共通基盤を、個人の技術力に任せず定義する。

## 8. 限界と改善案

### 8.1 現時点の限界

- キーワード検索は単純な方式である。検索語は固定のリストで、今回の規程と質問に合わせて用意したため、新しい質問には対応できない。同義語の追加も5語のみで、表記揺れや言い換えに弱い（Q5で確認）。
- 「精算」のような広いキーワードでは、関連の薄い行が多く混ざる。
- 取得できた行に必要な条件が揃っていても、回答に反映されるとは限らない（Q6で確認）。
- 規程の曖昧さは、検索処理だけでは解消できない。
- 評価は手動であり、採点者による判断の差が生じる可能性がある。
- 各質問は1回だけ実行しており、温度などの設定は既定値のため、再実行すると回答が変わる可能性がある。採点に使った実行結果は `results.csv` に保存している。
- 方式間で、指示文と出力の上限（Aは400トークン、BとCは200トークン）が完全には揃っていない。
- 質問数は10問で、規程は架空のデータである。実業務での品質を保証するものではない。
- 修正後の再実験は行っていない。以下の改善案は、いずれも効果を検証していない。

### 8.2 改善案（いずれも未検証）

1. **検索の改善：** 同義語・表記揺れへの対応の拡充（現在は5語のみ。例：「宿泊費」に加えて「宿泊」も検索語にする）、キーワードの一致数による行の点数づけと上位の行への絞り込み。さらにその先として、意味検索の検証。
2. **検索結果の自動確認：** `questions.json` に「答えに必要な規程行」の欄を追加し、検索で必要な行が取得できたかを自動で数える。
3. **回答指示の改善：** 重要な注意点や条件を省略しない指示を追加し、同じ質問を複数回実行して、Q6のような省略が減るかを確認する。
4. **採点基準の拡張：** 6.1の分類で採点する。Q5の期待回答も、「精算できると読めるが、規程に明記はないため、確認が必要」のように見直す。
5. **新しい質問での検証：** 改善の効果を確かめるには、今回の10問とは別の質問セットが必要である。同じ10問で調整すると、結果を見てから直したことになり、改善の効果とは言えない。
6. **運用面：** 規程の更新方法や参照範囲など、実運用を想定したデータ管理の検討。

## 9. 実行方法

事前にPython環境を用意し、必要なパッケージをインストールする。

```bash
pip install openai tiktoken
```

OpenAI APIキーは、環境変数 `OPENAI_API_KEY` に設定する。APIキーはソースコードや公開リポジトリに記載しない。

```bash
python answer_once.py      # 単一質問でのAPI動作確認
python answer_all_a.py     # A：モデル単体
python answer_all_b.py     # B：規程全文
python answer_all_c.py     # C：簡易RAG（キーワード検索）
python show_q1by1.py       # results.csv の回答を、質問番号を指定して3方式並べて表示（採点に使用）
```

- `results.csv` は、A・B・Cそれぞれの全問の出力テキストを、Pythonスクリプトでマージして作成した。採点に使った実行結果として同梱している。
- 使用モデルは `gpt-4.1-mini`。検証用に比較的安価なモデルを選んだ。
- API利用には別途料金が発生する（今回の規模では少額）。
- 規程と質問データは、検証用に作成した架空のデータである。

## 12. 実運用を想定した設計方針

経費精算FAQのような用途では、次の方針で設計することを考える。

- **方式の選択：** 規程が小さければ全文を渡す方式でも足りる。規程が大きい、更新が多い、コストが課題になる場合は、検索で関連情報に絞る方式を検討する。
- **検索と回答の検証を分ける：** 「検索結果に必要な情報が含まれているか」と「回答が正しいか」を、別々に確認する。
- **回答の示し方：** 回答には、根拠となる規程の参照先を付ける。規程に明記された内容と、推論として読み取った内容を区別して示し、不明な点は断定せず、経理などへの確認を案内する。
- **人の役割：** AIは問い合わせ対応を補助する位置づけとし、例外処理や最終判断は、既存の人による確認フローを維持する。
- **効果の測定：** 回答品質に加えて、問い合わせ件数や対応時間の変化も評価する。今回の検証では、これらは測定していない。

## 13. まとめ

経費精算FAQという具体的なユースケースで、API連携、コンテキストの与え方（モデル単体・規程全文・簡易RAG）、回答の評価を一通り実装し、10問で比較しました。

- 規程全文を渡した方式は期待回答との一致が最も高く（10/10）、簡易RAGは合計トークン数をおよそ半分に抑え、根拠との整合性が最も高くなりました（10/10。期待回答との一致は8/10）。ただし、10問・架空の規程・キーワード検索という条件での結果であり、方式の優劣を一般化するものではありません。
- 一致しなかった2問を調べると、Q5は検索漏れと規程の曖昧さの重なり、Q6は検索で必要な情報が取れていたのに、回答で注意点が省略されたケースでした。原因は、実際に渡した情報を確認するまで分かりませんでした。
- 正解か不正解かの採点では、規程にない結論の断定（Q5のB）や、条件付きの表現の断定化（Q10のB）を十分に捉えられません。評価の観点を増やす必要があります。
- 改善案（キーワードの見直し、検索結果の自動確認、回答指示の改善、採点基準の拡張）は、いずれも未検証です。効果を確かめるには、新しい質問セットが必要です。

生成AIの活用は、モデルの選択やプロンプトだけでなく、データの置き場所、検索、通常のプログラムと生成AIの役割分担、人による確認、評価の方法を含めて設計する必要があると学びました。
